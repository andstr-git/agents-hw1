# Design

## Context

См. `proposal.md` — Why. Проект greenfield: в `with-spec/` пока только бриф, исходные данные и приёмочные сценарии, кода нет. Ограничения, формирующие подход: статическое приложение без сборки и зависимостей, запуск из файловой системы, поддержка ширины 390 px, тесты без внешних пакетов.

## Goals / Non-Goals

**Goals:**

- Один источник истины для задач и вычисляемого представления (видимый список, итоги, прогресс).
- Чистое доменное ядро, тестируемое в Node без DOM.
- Минимальная и предсказуемая отрисовка: после любого изменения данные → пересчёт → рендер.
- Понятная деградация при недоступном `localStorage`.

**Non-Goals:**

- Фреймворки, сборщики, транспиляция, пакетный менеджер и `package.json`.
- Серверная часть, синхронизация, несколько пользователей, роутинг.
- Автоматизированная проверка вёрстки и пиксельных размеров: она остаётся ручной.
- Доступность сверх базовых подписанных полей и кнопок (полный аудит WCAG не проводится).

## Decisions

### 1. Два модуля: `domain.mjs` и `app.mjs`

`domain.mjs` содержит чистые функции без обращений к DOM и `localStorage`: создание задачи, валидация, добавление, удаление, переключение `done`, фильтрация, расчёт итогов и прогресса. `app.mjs` отвечает за состояние, хранение, DOM и связывание событий, а также экспортирует чистую функцию построения view-model.

Альтернатива — всё в одном `app.mjs`: меньше файлов, но логику нельзя проверить в Node без эмуляции DOM. Выбранное разделение следует требованию брифа и даёт тестам точку входа.

### 2. View-model как проверяемая граница интерфейса

`app.mjs` экспортирует `buildViewModel(tasks, filter)`, возвращающую: видимый список задач, `totalHours`, `doneHours`, `progress`, подписи фильтров и текст пустого состояния. DOM-рендер только отображает эту модель. Экспорт доступен и в браузере, и в Node; инициализация DOM выполняется только при `typeof document !== "undefined"`.

Альтернатива — тестировать DOM через `jsdom`: точнее, но нарушает запрет на внешние библиотеки. Компромисс: автоматические тесты проверяют данные и view-model, реальный DOM проверяется вручную по T1–T5.

### 3. Однонаправленный поток состояния

Состояние: `{ tasks: Task[], filter: "all" | "active" | "done" }`. Любая мутация (добавление, удаление, переключение) меняет `tasks`, затем вызывается `render()`, который пересобирает view-model и перерисовывает список и сводку. Форма находится вне перерисовываемого списка, поэтому введённые значения и фокус не теряются при изменении фильтра или статуса.

Альтернатива — точечное обновление отдельных узлов: меньше работы DOM, но выше риск рассинхронизации данных и интерфейса. При трёх–десятках задач полная перерисовка списка дешевле.

### 4. Валидация в домене, ограничения формы — как подсказка

Авторитетна доменная валидация: `title.trim() !== ""`; часы парсятся из строки, пустая строка и пробелы отклоняются до приведения к числу; число должно быть конечным, в диапазоне 0,5–24 и кратно 0,5. Кратность проверяется через `Math.round(hours * 2) / 2 === hours`, чтобы избежать ошибок двоичной арифметики. HTML-атрибуты `type="number"`, `min`, `max`, `step` дублируют правила для удобства, но не заменяют проверку.

Результат валидации — структура с ошибками по полям (`title`, `hours`), а не выброшенное исключение: интерфейсу нужно показать обе ошибки и сохранить введённые значения.

### 5. Прогресс и итоги считаются по всем задачам

`totalHours` и `doneHours` вычисляются по полному массиву, фильтр применяется только после этого и только к видимому списку. Прогресс: `totalHours > 0 ? Math.round(100 * doneHours / totalHours) : 0`; результат дополнительно проверяется на конечность, чтобы исключить `NaN`/`Infinity`. Округление — `Math.round`, как требует бриф (2/6 → 33 %).

### 6. Идентификаторы задач

Сиды получают стабильные строковые id (`seed-reading`, `seed-practice`, `seed-review`), новые задачи — `crypto.randomUUID()` при наличии, иначе счётчик с временной меткой. Стабильные id нужны для корректного удаления и переключения после перерисовки.

### 7. Персистентность с деградацией

Ключ `task-tracker.tasks.v1` хранит только массив задач; фильтр не сохраняется и сбрасывается в `all`. Доступность хранилища определяется однократной пробной записью в `try/catch`. При недоступности или ошибке записи показывается ненавязчивое сообщение «Сохранение недоступно — задачи хранятся до закрытия страницы», приложение продолжает работать в памяти. Повреждённый JSON игнорируется: загружается исходный пример, показывается сообщение о сбросе сохранённых данных. Запись выполняется после каждой успешной мутации.

Альтернатива — `IndexedDB`: избыточно для массива задач и усложняет код.

### 8. Тесты на встроенном раннере Node

`tests/acceptance.test.mjs` использует `node:test` и `node:assert/strict`, импортирует `domain.mjs` и `buildViewModel` из `app.mjs`. Каждый сценарий T1–T5 покрывается на уровне данных и view-model: состав списка, `totalHours`, `doneHours`, `progress`, ошибки валидации, пустое состояние. Запуск: `node --test tests/acceptance.test.mjs`. `package.json` не добавляется, чтобы не расширять состав артефактов.

### 9. Разметка и стили

`index.html` — семантическая структура: заголовок, сводка, форма с `<label>` у каждого поля, группа фильтров, список задач. `styles.css` — mobile-first, `max-width`, отсутствие фиксированных ширин и `100vw`-элементов, перенос длинных названий, крупные зоны нажатия. Горизонтальный скролл исключается через `box-sizing: border-box` и `min-width: 0` у гибких элементов.

## Risks / Trade-offs

- **DOM-рендер не покрыт автоматическими тестами** → риск расхождения данных и интерфейса. Смягчение: весь расчёт вынесен во view-model, DOM-слой остаётся тонким; ручная проверка T1–T5 в браузере на ширине 390 px.
- **Полная перерисовка списка** → возможная потеря фокуса на элементах внутри списка. Смягчение: форма и фильтры вне перерисовываемой области; при необходимости фокус восстанавливается после рендера.
- **`localStorage` может быть недоступен или переполнен** → потеря сохранности. Смягчение: `try/catch`, пробная запись, сообщение пользователю, работа в памяти.
- **Проверка шага 0,5 на числах с плавающей точкой** → ложные отказы. Смягчение: сравнение через удвоение и округление, покрытие границами 0,5, 1,5, 24 и значениями 0,4, 1,3, 24,5 в тестах.
- **Горизонтальный скролл на 390 px** → требование читаемости. Смягчение: перенос текста, отсутствие фиксированных ширин, ручная проверка в DevTools.

## Migration Plan

Миграция не требуется: изменение создаёт приложение с нуля, существующие данные и API не затрагиваются. Откат — удаление добавленных файлов; сохранённые данные в `localStorage` остаются локально и не влияют на другие приложения.
